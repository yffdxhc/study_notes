# 在岗学习 · 导读

> **用途**：手上出现一个现象时，先判断"这是哪一类问题、该翻哪一篇的哪一节"，再去读。
>
> **用法**：**不要按顺序通读。** 这三篇是参考手册，不是课文。查一次算一次，查两次就记住了。
>
> **⚠️ 定位（最重要）**：这个模块写的**不是公司问题记录**，而是 **AOSP / 平台的标准行为说明**。
> 目标是回答「**这个功能在 AOSP 里长什么样**」——换公司、换项目、换 MTK/高通，知识照样成立。
> **公司源码、真实日志、客户包名、项目代号一律不落盘。**
>
> **为什么需要它**：五篇加起来 1800+ 行，每篇 6~7 个部分。累的时候想"系统学一遍"必然抓不住重点，正确做法是**带着现象进来、带着答案出去**。这份导读就是那张对照表。

## 二、五篇之间的关系

**前三篇是时间线上的三段；第四、五篇是两个横切面。**

```
【时间线】同一台设备

① 开机流程          上电 → 内核 → init → zygote → system_server → 桌面
                                                              ↓
② AOSP源码路径导读   App 启动 / 进小窗：窗口怎么被创建、怎么被动画、怎么上屏
                                                              ↓
③ 锁屏闪屏           锁屏 → 窗口被移除 → 空档 → 屏幕熄灭


【横切面 A】东西怎么被区分

④ Overlay 与配置     同样的流程，不同机型 / 不同 SKU 的差异参数从哪来


【横切面 B】边界怎么划

⑤ EdgeToEdge 与 Insets   系统栏那块白，谁负责避让（框架还是应用）
```

**递进关系：**

| 层 | 讲的是 | 关键共性 |
|---|---|---|
| ① | **东西怎么起来** | 多级接力、每级只做"校验→加载→跳转" |
| ② | **东西怎么动** | 转场框架（Transition）+ 临时 leash |
| ③ | **东西怎么没** | 同样是 leash 被移除，同样是"两个动作之间的时间差" |
| ④ | **差异怎么表达** | 资源找 overlay、开关找 property、身份找 SKU |
| ⑤ | **职责怎么划** | 框架消费 insets？应用自己避让？——**边界一变，所有间距都要重算** |

> **②和③是同一个机制的两个方向**（②窗口被 leash 带着动，③leash 销毁时窗口跟着没）；
> **④⑤则是两个横切面**——④讲「同样的代码凭什么在不同机器上不同」，⑤讲「同一块空白凭什么由不同角色负责」。

## 九、写这类笔记的两条红线

### 9.1 脱敏：哪些能写、哪些不能写

> **核心区别**：**关键词**是通用资产，**前缀和取值**才是公司数据。

| ✅ 可以写 | ❌ 不要写 |
|---|---|
| AOSP 的类名、方法名、源码路径 | 公司仓库的分支名、commit、内部 patch |
| 公开的厂商术语（preloader、LK、ABL、EDL） | 客户包名、机型、项目代号 |
| **日志关键词本身**（`onClick`、`canDoFastAnimation`） | 私有 log tag 的**前缀**、内部命名空间 |
| **关键词挂在 AOSP 哪个环节** | 私有 flag 的**取值组合**、完整日志行 |
| 通用的量级判据（<100ms、约 500ms） | 原始日志文本、日志行号、绝对时间戳 |
| AOSP 官方行为（cs.android.com 可查） | 客制化的具体实现代码 |

> **一句话**：写「**关键词 + 它挂在 AOSP 哪个环节 + 客制化改了什么**」，不写「**这次完整抓到了什么**」。

### 9.2 关键词回溯法（这一节比其他都重要）

**先纠正一个错误做法**：不要写「这个 flag AOSP 里没有」就完事——**那等于把线索扔了。**

公司的客制化逻辑，**本质上是对 AOSP 某个流程的定制**，离不开 AOSP 底层。所以：

> **关键词不是「是不是 AOSP 的」问题，而是「它挂在 AOSP 哪个环节」的问题。**

```
陌生关键词
   → ① 它挂在 AOSP 的哪个环节？（启动 / 动画 / 电源 / 窗口 / 输入…）
   → ② AOSP 在这个环节的标准实现是什么？（cs.android.com 查）
   → ③ 客制化在这里改成了什么？（只记差异点，不记实现细节）
```

**写笔记时给每个关键词配三列：**

| 关键词 | 挂在 AOSP 哪个环节 | AOSP 标准实现 | 客制化 |
|---|---|---|---|
| `onClick` | 桌面图标点击 → 发起启动 | Launcher3 `BubbleTextView#onClick` | 无 |
| `canDoFastAnimation` | **App 启动时"播不播打开动画"的决策** | `ActivityOptions` + WM Shell `DefaultTransitionHandler` | **多了一条"提前启动"分支** |

> **只答「是/不是」得到一句话；答「挂在哪一环」能得到「AOSP 本来怎么走 + 客制化改成什么」——这才叫学 AOSP。**
> 换公司、换项目、换芯片平台，**标识符会变，环节不会变。**

### 9.3 每篇都按这个三段式写

以后新增笔记，统一回答三个问题：

| 段 | 回答什么 | 例（锁屏闪屏） |
|---|---|---|
| **① AOSP 标准流程** | 这功能在 AOSP 里怎么走？谁调谁？ | `lockNow` → DevicePolicyManagerService → `goToSleep` → keyguard + PowerManager |
| **② 怎么定位** | 搜哪些关键词、看哪类日志、什么量级判据 | 搜 `lockNow, callingPkg`，算 RESUME→lockNow 间隔 |
| **③ 客制化改在哪** | 偏离标准流程的位置 → 对应的 AOSP 环节 | 启动动画决策多了一条"提前启动"分支 |

> **①永远成立**（换公司也不变），②是可复用技能，③是判断力。
> 三段写好了，笔记就从「这次的答案」变成「下次的工具」。
