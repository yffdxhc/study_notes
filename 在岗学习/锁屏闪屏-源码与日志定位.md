## 一、整体流程：从点击图标到屏幕熄灭

### 1.1 五个进程的流水线

原生 Android（AOSP）上，"点击桌面图标 → App 打开 → App 调 lockNow 锁屏 → 屏幕熄灭"是一条跨 **5 个进程**的流水线：

| # | 谁 | 做什么 |
|---|---|---|
| 1 | **桌面进程**（AOSP 是 Launcher3） | 图标被点击，发起启动；同时启动过渡动画（图标放大成 App 窗口），壁纸跟着做缩放动画 |
| 2 | **system_server**（ActivityTaskManagerService） | 创建 App 的 Task，启动 App 进程；Android 12+ 会先显示系统启动画面（SplashScreen） |
| 3 | **App 进程** | Activity 走到 RESUME，界面真正可见 |
| 4 | **system_server**（DevicePolicyManagerService） | App 调 `lockNow`，校验设备管理员权限后，触发熄屏 + 显示锁屏 |
| 5 | **SystemUI + 电源服务** | 锁屏界面画出来，屏幕真正熄灭 |

**闪屏就发生在第 4、5 步之间**：App 的窗口被锁屏过渡移除了，但屏幕还没熄，中间空了几百毫秒，露出底层内容。

### 1.2 七个关键词的总览（按时间顺序出现）

```
onClick / startActivity          ← 桌面发起启动
setFlags 0(show)                 ← App 窗口上屏
ACVTIVITY_STATE_RESUME           ← App 界面可见
lockNow, callingPkg              ← App 调锁屏
onStartedGoingToSleep            ← 系统开始锁屏
setFlags 1(hide)                 ← App 窗口被移除
power_screen_state [0,1,...]     ← 屏幕熄灭
```

> **把这 7 个关键词按时间排出来，整个流程就还原了。**
> **闪屏窗口 = `setFlags 1(hide)` 到 `power_screen_state` 的差值。**

## 二、前半程：App 是怎么被拉起来的

### 2.1 源码视角

| 环节 | 源码位置 | 说明 |
|---|---|---|
| **桌面点击入口** | `packages/apps/Launcher3` 的 `BubbleTextView#onClick` → `Launcher#launchIntent` | 发起启动 |
| **过渡动画** | `frameworks/base/libs/WindowManager/Shell/…/transition/` 的 `Transitions`、`DefaultTransitionHandler` | 图标放大成 App 窗口的动画由 **WM Shell 驱动，不是桌面自己画的** |
| **壁纸动画** | `frameworks/base/services/core/…/server/wm/` 的 `WallpaperController`、`WallpaperWindow` | 壁纸是独立窗口，层级在所有 App 之下、桌面之上。App 从桌面打开时壁纸做缩放/模糊过渡——**这一步会露出壁纸，是原生行为，Pixel 上同样存在** |

### 2.2 关键词怎么读：从关键词回溯到 AOSP 环节

**核心认知**：私有日志里的关键词，**不是"AOSP 的名字"，而是"指向 AOSP 某个环节的路标"**。

公司做的客制化逻辑，**一定是对 AOSP 某个流程的定制**——名字可以改，**环节不会变**。所以每个陌生关键词都能这样用：

```
陌生关键词
   → ① 它挂在 AOSP 的哪个环节？（启动？动画？电源？）
   → ② AOSP 在这个环节的标准实现是什么？
   → ③ 客制化在这里改成了什么？
```

| 关键词 | 挂在 AOSP 哪个环节 | AOSP 标准实现 | 客制化 |
|---|---|---|---|
| `onClick` | 桌面图标点击 → 发起启动 | Launcher3 `BubbleTextView#onClick` | 无 |
| `ShortcutIcon` | 桌面图标 / 快捷方式模型 | Launcher3 图标与 shortcut 的数据模型 | 无（⚠️ 命名待核） |
| `canDoFastAnimation` | **App 启动时"播不播打开动画"的决策** | `ActivityOptions` 启动动画 + WM Shell `DefaultTransitionHandler` | **多了一条"提前启动"分支** |
| `startAppOpenWallpaperAnimation` | 桌面 → App 的壁纸过渡 | `WallpaperController` | 无明显改动（⚠️ 方法名待核） |

> **所以关键不是"这个 flag 是不是 AOSP 的"，而是"它挂在哪个 AOSP 环节上"。**
> 前者只能得出「是 / 不是」；后者能得出「**AOSP 这里本来怎么走，客制化改成了什么**」——
> **这才叫从日志学 AOSP。**

原始日志形如（**前缀已脱敏，关键词保留**）：

```
<私有前缀>_Launcher.ShortcutIcon: onClick: canBreakCloseAnim:false, canQuickOpen:false
<私有前缀>_Launcher.ShortcutIcon: onClick: canDoFastAnimation = true; finalIsSameTask = false
```

> **`canDoFastAnimation = true` 是定音行**：桌面决定走"快速启动"（提前启动）路径。
> 判断原则——App 启动即锁屏，这种点击**不该**走提前启动，应按包名屏蔽这条路径。

### 2.3 其余日志关键词

```
startAppOpenWallpaperAnimation     ← 壁纸"App打开"动画启动（关键！只在桌面图标打开时触发）
setFlags 0(show)                   ← App 窗口上屏（SurfaceFlinger 记录）
ACVTIVITY_STATE_RESUME : <包名>    ← App 的 Activity 走到 RESUME
```

### 2.4 理解要点

> **`startAppOpenWallpaperAnimation` 是后面闪屏的伏笔。**

它启动时桌面壁纸开始做打开动画；如果 App 很快锁屏，这个动画正露着的壁纸就会出现在闪屏空档里。

**从应用商店打开时日志里没有这个关键词**，这正是"桌面闪、商店不闪"的差异点。

## 三、锁屏触发：`lockNow` 在源码里做了什么

### 3.1 源码视角

| 侧 | 源码位置 | 做什么 |
|---|---|---|
| **App 侧入口** | `frameworks/base/core/java/android/app/admin/DevicePolicyManager#lockNow()` | App 调的 API，要求 App 是**已激活的设备管理员**（DeviceAdmin） |
| **服务端** | `frameworks/base/services/devicepolicy/…/DevicePolicyManagerService#lockNow()` | ① 校验调用方是不是激活的设备管理员；② 触发熄屏流程（`goToSleep`）+ 通知 SystemUI 显示锁屏 |

### 3.2 日志关键词

```
lockNow, callingPkg:<包名>                  ← 谁调的锁屏
onStartedGoingToSleepAsync                  ← 系统开始进入睡眠
onStartedGoingToSleep instantlyLock=true    ← 立即锁屏（不是超时）
```

### 3.3 理解要点

**① 时间差小于 100ms = 点开即锁屏**

> 这类问题的日志里 `ACVTIVITY_STATE_RESUME` 到 `lockNow, callingPkg` **常只隔几十毫秒**——App 界面刚可见就锁屏了。
>
> **判断方法很简单：grep 这两个关键词，算时间差，小于 100ms 基本坐实。**

**② 日志里没有"App 主动关闭"**

搜 `wm_finish_activity`、`finishActivity` 都是空的——**App 没有主动关闭自己的界面**，是后面的锁屏过渡把它的窗口移除的。

> 这修正了"应用弹框消失太早"的说法：**不是 App 关早了，是系统过渡移除了它。**

## 四、空档：为什么"显示锁屏"和"屏幕熄灭"是两回事

**这是闪屏实际发生的地方，也是最反直觉的一点。**

> **"显示锁屏界面"和"屏幕熄灭"是两个独立动作，中间隔着几百毫秒。**

### 4.1 源码视角：两条完全不同的路径

| 动作 | 源码位置 | 负责组件 |
|---|---|---|
| **锁屏显示** | `frameworks/base/packages/SystemUI/…/keyguard/KeyguardViewMediator` | `onStartedGoingToSleep` → `showKeyguard`，把锁屏界面（壁纸、时间、通知）画出来 |
| **屏幕熄灭** | `frameworks/base/services/core/…/server/power/PowerManagerService#goToSleep()` → `updatePowerState()` → `DisplayPowerController` | 真正控制面板的电源状态 |

**两者由不同组件负责、走不同路径**，所以 keyguard 画完到屏幕真熄，中间有几百毫秒。**这几百毫秒里，锁屏界面是显示在还亮着的屏幕上的。**

### 4.2 日志关键词

```
doKeyguard: showing the lock screen    ← 锁屏界面开始显示
showKeyguard - shouldDelay:false       ← 确认显示
power_screen_state: [0,1,0,0,xxx]      ← 屏幕熄灭（[0,1]=灭，[1,0]=亮）
```

### 4.3 典型时序（相对时间）

```
T+0ms      doKeyguard: showing the lock screen   ← 锁屏显示
T+526ms    power_screen_state [0,1,...]          ← 屏幕熄灭
```

> **锁屏显示比熄屏早 526 毫秒。**
>
> 深色主题下用户看到的"锁屏壁纸先亮一下再黑屏"，就是这 526 毫秒——锁屏界面在亮屏上显示了半秒。
> **这是 AOSP 标准时序，不是任何特定实现的问题。**

## 五、完整拼图：窗口移除 + 三个对照实验

### 5.1 闪屏的完整机制

```
App 窗口上屏 → RESUME → lockNow → 锁屏过渡移除 App 窗口
                                          ↓
              ⚠️ 空档：窗口没了、屏幕还亮着、底层内容露出
                                          ↓
                                    屏幕熄灭
```

### 5.2 窗口移除的证据

```
setFlags 1(hide)                          ← App 窗口被隐藏（SurfaceFlinger）
onHandleDestroyed ... transition-leash    ← 窗口句柄销毁，"transition-leash"说明是系统过渡干的
```

> **`transition-leash` 这个词很关键**：它是 WM Shell 过渡动画的"牵引绳"，窗口挂在这上面说明**移除动作来自系统过渡，不是 App 自己**。

### 5.3 三个对照实验（都在日志里）

| 对照组 | 差异 | 结论 |
|---|---|---|
| **桌面打开 vs 应用商店打开**（同一份日志） | 桌面路径有 `startAppOpenWallpaperAnimation`，商店路径没有 | 桌面闪、商店不闪 → **壁纸动画是放大器** |
| **App 锁屏 vs 超时熄屏**（同一份日志） | 超时熄屏的窗口内，搜 App 窗口移除、壁纸动画、`lockNow` 全空 | 官方锁屏不闪 → **差异项就是"App 窗口被移除"** |
| **本机 vs Pixel**（实测） | Pixel 上也有概率闪到桌面 | 基础机制在 AOSP 标准逻辑内，**根因在 App 的"点开即锁屏"**，桌面侧的快速启动动画只是让闪更明显 |

### 5.4 责任归属

| 方 | 责任 | 具体问题 |
|---|---|---|
| **App** | **主责** | 启动即锁屏；用会被过渡移除的普通 Activity 做锁屏前界面 |
| **桌面** | 可缓解 | 对这类 App 屏蔽快速启动动画 |
| **系统锁屏侧** | **无责** | keyguard 早于熄屏是标准时序 |

## 六、关键词速查表 + 通用排查方法

### 6.1 速查表

| 关键词 | 挂在 AOSP 哪个环节 | 含义 | AOSP 标准实现 |
|---|---|---|---|
| `onClick` / `startActivity` | 桌面 → 发起启动 | 桌面发起启动 | Launcher3 `BubbleTextView#onClick` |
| `canDoFastAnimation = true` | **App 启动动画的"播不播"决策** | 走"快速启动"（提前启动），空档会露桌面 | `ActivityOptions` + WM Shell `DefaultTransitionHandler`（**客制化在此加了分支**） |
| `startAppOpenWallpaperAnimation` | 桌面 → App 的壁纸过渡 | 壁纸打开动画（会露壁纸） | `WallpaperController` / `WallpaperWindow` |
| `setFlags 0(show)` / `1(hide)` | SurfaceFlinger 的层可见性 | 窗口上屏 / 移除 | SF layer flags |
| `ACVTIVITY_STATE_RESUME` | ATMS 的 Activity 生命周期 | App 界面可见 | `ActivityTaskManagerService` |
| `lockNow, callingPkg` | DevicePolicy 的锁屏入口 | 谁调的锁屏 | `DevicePolicyManagerService#lockNow` |
| `onStartedGoingToSleep` | 锁屏/电源的睡眠入口 | 系统开始锁屏 | `KeyguardViewMediator` |
| `doKeyguard: showing the lock screen` | Keyguard 的显示流程 | 锁屏界面显示 | `KeyguardViewMediator#showKeyguard` |
| `power_screen_state [0,1,...]` | 电源管理的亮灭屏 | 屏幕熄灭 | `PowerManagerService` |
| `transition-leash` | WM Shell 的转场 | 系统过渡在牵引窗口 | WM Shell Transitions |

> **这张表真正有用的地方：10 个关键词，全都能挂到 AOSP 的某个环节上。**
>
> 唯一的 `canDoFastAnimation`，也不是"AOSP 里没有的野东西"——它是挂在
> **「App 启动时播不播打开动画」这个 AOSP 环节**上的一条**客制化分支**。
>
> **结论：闪屏机制 = 100% 的 AOSP 骨架 + 1 条客制化分支。**
> 知道骨架，才知道那条分支加在哪；不知道骨架，看到的就是一堆陌生 tag。
>
> ⚠️ `ACVTIVITY_STATE_RESUME` 这个拼写（多一个 `T`）是**日志本来的 tag**，搜的时候照抄，别改。

### 6.2 通用排查六步（下次"点开 App 闪一下"直接套）

1. **认 pid** —— 桌面、App、system_server、SurfaceFlinger、SystemUI 各说各话，**结论在时间戳对齐里**
2. **算 `RESUME` → `lockNow` 间隔** —— **< 100ms = 点开即锁屏**（根因信号）
3. **搜 `canDoFastAnimation` / `startAppOpenWallpaperAnimation`** —— 有 = 走了提前启动、空档露桌面
4. **算 `setFlags 1(hide)` → `power_screen_state` 差值** = 闪屏窗口
5. **找同日志内"无 App 参与的锁屏"**（超时熄屏）作对照组，**差异项即责任项**
6. **跨系统对照** —— 原生也闪 → 根因在 App；只有定制闪 → 根因在定制层
